# План имплементации приложения для автомоек

Документ фиксирует целевую архитектуру Django-приложения для записи клиентов на автомойку и планирования работы руководителем: загрузка боксов, смены мойщиков, назначения на заказы, переносы и отмены.

## 1. Контекст текущего проекта

Проект уже содержит Django backend в `back/` и несколько приложений:

- `cars` - справочники марок, моделей и типов автомобилей.
- `customer` - клиенты и автомобили клиентов.
- `personal` - мойщики, города, районы, станции и табель.
- `car_wash` - типы мойки, длительности, стоимости и аванс.
- `main` - текущая модель `Schedule`, которая частично описывает запись в расписании.

В текущем виде приложение хранит базовые справочники, но еще не имеет полноценного ядра бронирования: боксов, статусов заказа, точных смен, проверки пересечений, API доступности и управленческого календаря.

## 2. Цель MVP

MVP должен позволять:

1. Клиенту выбрать станцию, автомобиль, тип мойки, дату и свободное время.
2. Системе автоматически рассчитать длительность, стоимость, аванс и остаток.
3. Системе зарезервировать свободный бокс и доступных мойщиков.
4. Руководителю видеть расписание по станции, боксам и мойщикам.
5. Руководителю назначать мойщиков, переносить записи, отменять записи и менять статус выполнения.

## 3. Архитектурные принципы

- Бизнес-логику планирования вынести из `views.py` в сервисный слой.
- Модели должны описывать факты: клиент, автомобиль, услуга, смена, бокс, запись, назначение.
- API должен использовать одну и ту же сервисную логику, что и админка или будущий frontend.
- Проверка пересечений должна выполняться перед созданием и переносом записи.
- Справочники цен и длительностей должны оставаться отдельными, чтобы руководитель мог менять тарифы без изменения кода.
- В MVP можно оставить SQLite, но архитектуру строить так, чтобы позже перейти на PostgreSQL.

## 5. Целевая модель данных

### 5.1 Существующие справочники

Сохранить и доработать:

- `cars.CarType`
- `cars.CarBrand`
- `cars.CarModel`
- `cars.CarDescription`
- `personal.WashStation`
- `personal.Washer`
- `car_wash.WashType`
- `car_wash.WashDuration`
- `car_wash.WashCoast`
- `car_wash.DownPayment`

Важно: модель `WashCoast` содержит опечатку в названии. На отдельном этапе лучше переименовать ее в `WashCost`, а миграцию сделать аккуратно, чтобы не потерять данные.

### 5.2 Новые и доработанные модели

#### `WashBox`

Бокс автомойки.

Поля:

- `wash_station` - станция.
- `name` - название или номер бокса.
- `is_active` - участвует ли бокс в расписании.
- `description` - необязательное описание.

Ограничения:

- уникальность `wash_station + name`.

#### `WasherShift`

Рабочая смена мойщика.

Поля:

- `washer` - мойщик.
- `wash_station` - станция.
- `starts_at` - начало смены.
- `ends_at` - конец смены.
- `is_active` - смена учитывается в планировании.

Ограничения:

- `starts_at < ends_at`.
- индексы по станции, мойщику и времени.

#### `Booking`

Запись клиента на мойку.

Поля:

- `customer` - клиент.
- `car` - автомобиль клиента.
- `wash_station` - станция.
- `wash_box` - назначенный бокс.
- `wash_type` - тип мойки.
- `starts_at` - начало записи.
- `ends_at` - окончание записи.
- `status` - статус записи.
- `cost` - рассчитанная стоимость.
- `down_payment` - рассчитанный аванс.
- `residual` - остаток к оплате.
- `comment` - комментарий клиента или менеджера.
- `created_at`, `updated_at`.

Статусы:

- `draft` - черновик.
- `pending` - создана, ждет подтверждения или оплаты.
- `confirmed` - подтверждена.
- `in_progress` - мойка началась.
- `completed` - мойка завершена.
- `cancelled` - отменена.
- `no_show` - клиент не приехал.

#### `BookingAssignment`

Назначение мойщика на запись.

Поля:

- `booking` - запись.
- `washer` - мойщик.
- `role` - роль в заказе, например основной или помощник.

Ограничения:

- уникальность `booking + washer`.

#### `ResourceBlock`

Блокировка ресурса.

Поля:

- `wash_station` - станция.
- `wash_box` - бокс, если блокируется бокс.
- `washer` - мойщик, если блокируется мойщик.
- `starts_at`, `ends_at` - период блокировки.
- `reason` - причина.

Использование:

- ремонт бокса;
- отсутствие мойщика;
- технический перерыв;
- закрытие станции.

### 5.3 Доработки клиента и автомобиля

Текущая модель `Customer` хранит одну машину через `car = ForeignKey(Car)`. Для реального сценария лучше:

- добавить связь `Customer.user` с `auth.User`;
- перенести связь к автомобилю в сторону `Car.customer`;
- разрешить клиенту иметь несколько автомобилей;
- телефон сделать уникальным или нормализованным.

Для MVP можно оставить текущую связь, но API сразу проектировать с учетом нескольких автомобилей.

## 6. Сервисный слой

### 6.1 `pricing.py`

Отвечает за расчет стоимости:

- найти цену по `car_type + wash_type + wash_station`;
- найти длительность по `car_type + wash_type + wash_station`;
- найти процент аванса по станции;
- вернуть `cost`, `down_payment`, `residual`, `duration`.

### 6.2 `availability.py`

Отвечает за свободные слоты:

1. Получить станцию, тип авто, тип мойки и дату.
2. Рассчитать длительность услуги.
3. Построить интервалы возможного начала записи.
4. Найти активные боксы станции.
5. Найти мойщиков, у которых есть активная смена на этот интервал.
6. Исключить пересечения с активными записями.
7. Исключить пересечения с `ResourceBlock`.
8. Вернуть список слотов с доступными боксами и мойщиками.

Активными для занятости считаются статусы:

- `pending`
- `confirmed`
- `in_progress`

Статусы `cancelled`, `completed`, `no_show` не должны блокировать будущие слоты.

### 6.3 `booking.py`

Отвечает за создание и изменение записей:

- создать запись;
- проверить доступность выбранного интервала;
- назначить бокс;
- назначить мойщика или мойщиков;
- перенести запись;
- отменить запись;
- сменить статус.

Все операции создания и переноса должны выполняться в `transaction.atomic()`.

## 7. API

### 7.1 Клиентские endpoints

- `GET /api/stations/` - список станций.
- `GET /api/car-types/` - типы автомобилей.
- `GET /api/wash-types/` - типы мойки.
- `GET /api/availability/?station=1&car_type=1&wash_type=1&date=2026-05-06` - свободные слоты.
- `POST /api/bookings/` - создать запись.
- `GET /api/my/bookings/` - мои записи.
- `PATCH /api/my/bookings/{id}/cancel/` - отменить свою запись.
- `PATCH /api/my/bookings/{id}/reschedule/` - перенести свою запись.

### 7.2 Управленческие endpoints

- `GET /api/manager/schedule/?station=1&date=2026-05-06` - расписание станции.
- `GET /api/manager/bookings/` - список записей с фильтрами.
- `PATCH /api/manager/bookings/{id}/assign/` - назначить бокс и мойщиков.
- `PATCH /api/manager/bookings/{id}/status/` - изменить статус.
- `POST /api/manager/shifts/` - создать смену мойщика.
- `POST /api/manager/resource-blocks/` - заблокировать бокс или мойщика.

## 8. Права доступа

Роли:

- `customer` - может создавать и смотреть только свои записи.
- `manager` - управляет расписанием доступных ему станций.
- `admin` - полный доступ ко всем справочникам и данным.

Для MVP можно использовать группы Django. В дальнейшем стоит добавить модель доступа менеджера к конкретным станциям.

## 9. Админка

Через Django admin нужно дать руководителю быстрый рабочий инструмент:

- станции;
- боксы;
- мойщики;
- смены;
- типы мойки;
- цены;
- длительности;
- записи;
- назначения мойщиков;

Для `BookingAdmin` нужны фильтры:

- дата;

## 12. Риски и решения

### Пересечение записей

Риск: две записи могут попасть на один бокс или одного мойщика.

Решение: проверять пересечения в сервисе бронирования внутри транзакции. При переходе на PostgreSQL добавить более строгие ограничения на уровне базы.

### Распыление логики между приложениями

Риск: часть записи находится в `main.Schedule`, часть в `car_wash`.

Решение: выбрать одну целевую модель `Booking` в `car_wash`, а `Schedule` использовать только как временное наследие или удалить после миграции данных.

### Неполная модель клиента

Риск: один клиент не сможет удобно хранить несколько автомобилей.

Решение: перенести связь автомобиля к клиенту через `Car.customer`, сохранив обратную совместимость на время миграции.

### Ошибка в названии `WashCoast`

Риск: опечатка будет размножаться в API и документации.

Решение: переименовать модель в `WashCost` отдельной миграцией до активной разработки API.

## 13. Что не входит в MVP

- Онлайн-оплата реальными платежными провайдерами.
- SMS и push-уведомления.
- Сложная оптимизация расписания.
- Мобильное приложение.
- Отчеты по выручке и зарплатам.
- Интеграция с бухгалтерией.

Эти части стоит добавлять после того, как стабильно заработают запись, доступность, статусы и управленческое расписание.
