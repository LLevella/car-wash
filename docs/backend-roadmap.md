# План дальнейшей разработки backend

Документ описывает backend-roadmap после выполненных этапов 1-13 из
`docs/implementation-plan.md`. Текущий backend уже умеет рассчитывать
доступность, создавать и переносить записи, управлять расписанием руководителя,
работать с session auth для SPA и отдавать базовые справочники для frontend.

Главная цель следующих этапов: стабилизировать API-контракты для frontend,
улучшить модель клиента и автомобиля, усилить права менеджеров по станциям и
подготовить систему к реальной эксплуатации без потери локальной поддержки
SQLite.

## 1. Принципы дальнейшей разработки

- SQLite остается поддержанным локальным и CI-вариантом без `DATABASE_URL`.
- PostgreSQL остается production-вариантом через `DATABASE_URL`.
- PostgreSQL-specific усиления можно добавлять только как дополнительный слой,
  с сервисной fallback-валидацией для SQLite.
- API должен сохранять regular JSON contract: `data` для успешных ответов,
  `detail` и `field_errors` для ошибок.
- Все новые backend endpoints покрываются тестами.
- Изменения модели данных делаются миграциями с обратной совместимостью там,
  где frontend уже зависит от контракта.
- Django admin остается инструментом администрирования справочников до тех пор,
  пока frontend не заменит конкретный сценарий.

## 2. Приоритеты

1. Стабилизировать API-контракт и ошибки форм.
2. Поддержать несколько автомобилей клиента.
3. Ограничить менеджеров конкретными станциями.
4. Усилить целостность бронирований и защиту от гонок.
5. Документировать API через OpenAPI и подготовить типы для frontend.
6. Добавить audit/observability для управленческих действий.
7. Подготовить production operations: CORS, Docker, backup, health/readiness.

## 3. Этапы разработки

### Этап 14. Единый API contract и ошибки

Задачи:

- Ввести helpers для successful/error responses.
- Привести ошибки всех API к формату:
  - `detail` - человекочитаемое описание;
  - `field_errors` - ошибки конкретных полей;
  - `code` - машинный код ошибки, где это полезно frontend.
- Убрать разнобой в статусах `400`, `401`, `403`, `404`.
- Добавить tests на ошибки booking, manager assign, auth и dictionary endpoints.
- Зафиксировать контракт в документации.

Критерии готовности:

- frontend может одинаково показывать ошибки форм на всех endpoints;
- старые successful payloads под `data` не сломаны;
- тесты покрывают минимум happy path и error path для ключевых endpoints.

### Этап 15. Несколько автомобилей у клиента

Задачи:

- Добавить связь `customer.Car.customer`.
- Оставить текущий `Customer.car` на переходный период или мигрировать данные
  аккуратной data migration.
- Обновить `GET /api/customers/cars/`, чтобы он возвращал все автомобили
  клиента.
- Добавить endpoints для клиента:
  - `POST /api/customers/cars/`
  - `PATCH /api/customers/cars/{id}/`
  - `DELETE /api/customers/cars/{id}/` или soft-delete.
- Обновить проверки booking: клиент может создать запись только на свою машину.
- Добавить manager lookup по customer.

Критерии готовности:

- текущие демо-данные мигрируют без ручных действий;
- клиент может иметь несколько автомобилей;
- существующий booking flow продолжает работать;
- тесты проверяют запрет записи на чужой автомобиль.

### Этап 16. Доступ менеджеров к станциям

Задачи:

- Добавить модель `ManagerStationAccess` или аналогичную связь user/station.
- Ограничить manager endpoints станциями, к которым есть доступ.
- Обновить schedule, booking list, assign, shifts и resource blocks.
- Добавить возможность admin видеть все станции.
- Обновить `seed_demo_data`, чтобы demo manager получил доступ к demo station.

Критерии готовности:

- manager не видит и не меняет записи чужой станции;
- admin сохраняет полный доступ;
- фильтры manager API учитывают station access;
- тесты покрывают разрешенный и запрещенный доступ.

### Этап 17. Усиление целостности бронирований

Задачи:

- Проверить все операции создания, переноса и назначения на повторную проверку
  ресурсов внутри транзакции.
- Добавить блокировки чтения там, где это возможно без ломки SQLite.
- Для PostgreSQL подготовить дополнительный слой ограничений от пересечений:
  exclusion constraints или отдельные resource reservation rows.
- Для SQLite сохранить сервисную проверку пересечений как основной механизм.
- Добавить стресс-тесты сервисного уровня на конфликтующие интервалы.

Критерии готовности:

- две активные записи не могут занять один бокс в одно время;
- один мойщик не может быть назначен на пересекающиеся активные записи;
- SQLite tests продолжают проходить;
- PostgreSQL-specific ограничения изолированы и документированы.

### Этап 18. Улучшение manager schedule API

Задачи:

- Добавить компактный payload для временной сетки дня.
- Вернуть вычисленные границы дня, шаг сетки и агрегаты загрузки.
- Добавить быстрые filters: `station`, `date`, `status`, `washer`, `box`.
- Поддержать partial refresh после изменения одной записи.
- Добавить endpoint деталей записи для manager:
  - `GET /api/manager/bookings/{id}/`

Критерии готовности:

- frontend может рисовать расписание без дополнительных вычислений в UI;
- manager видит загрузку боксов и мойщиков;
- payload остается приемлемым по размеру для одного дня.

### Этап 19. OpenAPI и типы для frontend

Задачи:

- Подключить OpenAPI tooling, например `drf-spectacular`.
- Описать схемы auth, dictionaries, booking, availability и manager API.
- Добавить endpoint `/api/schema/` и Swagger/ReDoc только для dev/admin.
- Настроить CI check генерации схемы.
- Подготовить frontend к генерации TypeScript types.

Критерии готовности:

- OpenAPI schema генерируется в CI;
- frontend может сверять типы API-контрактов;
- документация не раскрывает лишние production-данные.

### Этап 20. Audit log для управленческих действий

Задачи:

- Добавить модель `AuditEvent`.
- Логировать:
  - создание записи;
  - перенос;
  - отмену;
  - смену статуса;
  - назначение бокса/мойщика;
  - создание смены;
  - создание блокировки ресурса.
- Хранить actor, action, entity type/id, timestamp и diff/context.
- Добавить manager/admin endpoint для просмотра истории записи.

Критерии готовности:

- по каждой записи можно восстановить историю действий;
- audit write не ломает основную операцию без явной причины;
- тесты проверяют создание audit events.

### Этап 21. Notifications-ready слой

Задачи:

- Добавить `NotificationOutbox`.
- Создавать outbox events на booking created/rescheduled/cancelled/status
  changed.
- Пока не подключать реальный SMS/email provider.
- Добавить management command для обработки outbox в dev.

Критерии готовности:

- события уведомлений фиксируются транзакционно рядом с изменением записи;
- повторная обработка outbox безопасна;
- реального внешнего провайдера можно подключить отдельным этапом.

### Этап 22. Payment-ready слой

Задачи:

- Добавить payment status в booking или отдельную модель `Payment`.
- Разделить расчет аванса и факт оплаты аванса.
- Подготовить поля provider/payment reference без интеграции реального
  провайдера.
- Обновить статусы и права изменения booking после оплаты.

Критерии готовности:

- backend различает рассчитанный аванс и оплаченный аванс;
- booking flow готов к будущей онлайн-оплате;
- без payment provider система продолжает работать вручную.

### Этап 23. Production operations

Задачи:

- Настроить CORS/CSRF для separate frontend host, если frontend будет жить на
  другом домене.
- Добавить readiness endpoint, который проверяет database connection.
- Подготовить Dockerfile/docker-compose для backend + database.
- Описать backup/restore SQLite и PostgreSQL.
- Добавить management command для health diagnostics.

Критерии готовности:

- локальный Docker запуск не заменяет обычный SQLite dev-flow, а дополняет его;
- production health/readiness можно использовать в deploy;
- backup и restore описаны в docs.

### Этап 24. Отчеты MVP+

Задачи:

- Добавить manager endpoints для дневных агрегатов:
  - число записей;
  - выручка по статусам;
  - загрузка боксов;
  - загрузка мойщиков.
- Считать только completed/paid там, где это применимо.
- Добавить фильтры по станции и периоду.

Критерии готовности:

- руководитель получает базовые цифры по дню/неделе;
- расчеты покрыты тестами;
- отчетные endpoints не мешают основному booking flow.

## 4. Рекомендуемый порядок ближайших работ

1. Этап 14: единый API contract и ошибки.
2. Этап 15: несколько автомобилей клиента.
3. Этап 16: доступ менеджеров к станциям.
4. Этап 18: manager schedule API для удобного frontend.
5. Этап 19: OpenAPI и типы.

Этап 17 можно делать параллельно с переходом на PostgreSQL в staging, но
сервисная проверка конфликтов должна остаться рабочей на SQLite.

## 5. Definition of Done для backend-этапа

- Есть миграции, если менялась модель данных.
- `python manage.py makemigrations --check --dry-run` проходит.
- `python manage.py migrate --noinput` проходит на SQLite.
- `python manage.py check --deploy --fail-level WARNING` проходит с
  production-like env.
- Тесты проходят.
- Coverage не ниже текущего CI-порога.
- Документация обновлена: roadmap, README или frontend plan, если менялся
  публичный API.
- Коммит содержит только связанный набор backend-изменений.

## 6. Что пока не делать

- Не удалять поддержку SQLite.
- Не переписывать backend на другой framework.
- Не заменять Django admin полностью до появления конкретных frontend-экранов.
- Не подключать реальные платежи или SMS до стабилизации booking/status flow.
- Не добавлять websocket/polling, пока обычный schedule API справляется с
  нагрузкой.
